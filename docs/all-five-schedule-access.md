# Proposed access for daily hosted demo updates

The 13:00 UTC job should consider all five components. Two Jaeger and HotROD image refreshes run daily. Three infrastructure and application components reconcile when their tracked configuration changes. The selection recorded after the manual handover includes all five immediately. Keep the recovery policy set to `required` for scheduled OpenSearch maintenance. This document proposes access for the schedule. The operator has approved its component scope. Production access, resource creation, first execution and future Helmfile adoption have separate approval records.

## What to authorize

Use a dedicated API-only OCI identity for the main-only GitHub `demo-scheduled` environment, with the same cluster-authentication scope as the existing demo identities. Keep the human-reviewed `demo-apply` account and environment available for manual operation. The scheduled principal needs Kubernetes API access to the named demo resources. The existing OCI CSI driver performs backup, volume creation and attachment using its own identity. The scheduled principal needs no direct OCI IAM, Compute, block-volume administration or ability to manage cluster nodes.

An initial access change can authorize creation of the dedicated identity, its GitHub environment and its read-only discovery permissions while the activation variable is off. Set the environment's custom branch rule to `main`. Deliver key material via the environment and the separately approved project vault custody procedure. Ensure protected-main changes to workflows and deployment code require review because an eligible job can receive the environment credential.

For writes, authorize named in-place release updates, the six releases' Helm histories, and only the recovery operations below after the applicable enforcement has been rehearsed. Have an independently administered executor handle the privileged monitoring work with a verified, approved chart and values bundle or install equivalent object-content admission checks. Changing a Prometheus controller workload can convey its cluster-wide authority over Secrets through its service account. A generic reusable signer with unconstrained writes to the operator, hook jobs, RBAC or webhooks is substantially more powerful than the schedule requires. Keep scheduled writes disabled until the accepted monitoring execution path is in place. A human-approved manual monitoring transaction can cover maintenance in the meantime with separately verified access. Closing unattended acceptance requires running all selected components successfully through the agreed scheduled path.

## API operations and limits

| Purpose | Scope and verbs |
| --- | --- |
| Deployment and health reads | GET the four named namespaces, named render objects and Services. GET/LIST/WATCH workload rollout and readiness kinds used by Helm and kubectl, including Pods, Deployments, ReplicaSets, DaemonSets, StatefulSets, Jobs, Services, Endpoints, and the specific CR kinds in the selected bundle. LIST events, Ingresses, Certificates and EndpointSlices where the verifier requires them. `kubectl cluster-info` needs `kube-system` Service LIST. Failure diagnostics read Pod logs via `pods/log` in affected namespaces. Redact before sharing diagnostic output. |
| Steady release updates | GET/PATCH the existing named chart and supplemental objects in the matrix. The five named kube-system Services require a separate namespace Role. Each scheduled success merge-patches only its key in the existing `default/jaeger-demo-deployment-revisions` ConfigMap. Helm hooks need exact CREATE/GET/DELETE lifecycle and their Job wait/list/watch. Add CREATE or DELETE for a chart difference and its rollback only after inspecting the object delta. Deny automatic namespace creation, broad uninstall/reinstall and volume expansion in this job. |
| Helm history | GET/LIST Secrets in the four release namespaces with the standard Helm Secret driver. These reads also expose other Secret data there. Restrict CREATE/UPDATE/DELETE with a fail-closed admission rule to canonical positive revision names and matching Helm type/owner/release/version labels. Release mapping is `default={jaeger,prometheus}`, `jaeger={jaeger}`, `opensearch={opensearch,opensearch-dashboards}`, `otel-demo={otel-demo}`. Validate CREATE on new object, UPDATE on old and new and DELETE on old. Include separately validated chart-owned Secret updates, such as the three named monitoring Secrets. Keep TLS and AI Secrets outside allowed writes. Read-only storage isolation requires a separate design. |
| OpenSearch recovery reads | Discover snapshot APIs. GET the exact source Pod, PVC, bound PV and preprovisioned retained class `jaeger-opensearch-oci-retain`. LIST Jaeger pods to select the live image. LIST/GET recovery snapshots in `opensearch`. GET controller-assigned VolumeSnapshotContent by name. Provision the one approved snapshot class once through the administrator if missing. |
| Recovery writes | CREATE namespaced VolumeSnapshot, PVC, ConfigMap and Pod using the exact run/attempt naming and prescribed specs. PATCH only the tested annotations on the run's snapshot and its cluster-scoped bound VolumeSnapshotContent. GET status, and DELETE only the run's disposable Pod after verification or cancellation. Guard snapshot source/driver, retained deletion policy, PVC data source, source capacity/class, pod security context, image digest, service account/token, mounts and anti-affinity. Validate content binding to this namespace and the unique source snapshot. Exclude deletion of backups, retained content, restore PVC/config and mutation of the source volume. |
| Live trace verification | Named Pod exec in `opensearch` for the live `opensearch-cluster-single-0` and the run's verification Pod. Jaeger verification port-forwards to the Pods resolved from `jaeger-collector` and `jaeger-query`. Rehearse actual pinned kubectl TCP upgrade transport and permit its required GET or CREATE on `pods/exec` and `pods/portforward`. Unrestricted namespace exec grants an interactive capability far beyond the scripted checks. For generated Pod names, restrict CONNECT by run-reviewed names/targets or perform the checks through a scoped executor. CLI label selectors alone cannot impose authorization. |
| Chart security objects and hooks | Separate named RBAC, webhook and hook objects from ordinary Helm patch rights. The monitoring hook service accounts use Kubernetes authorization for CRD updates, webhook changes and the hook Secret. Its admission ClusterRole permits changes to all validating/mutating webhook configurations under chart defaults. The regular operator ClusterRole has all verbs on cluster-wide Secrets, ConfigMaps and StatefulSets. Bind existing named roles only to their exact reviewed service accounts. Constrain admission target/CA handling, hook and controller images, commands, volumes and credentials to the approved bundle. Keep the CI actor outside policy administration and arbitrary impersonation. |

Kubernetes RBAC `resourceNames` can select existing objects for named actions. It cannot restrict a top-level CREATE to a name prefix. Role/ClusterRole changes and bindings trigger additional privilege-escalation checks. Some monitoring roles have permissions the deployer should never receive directly. A protected executor can perform those reviewed transactions. If granting named `bind` or `escalate` to do this in-cluster, pair it with independent, fail-closed content and subject enforcement and test rollback to the prior approved definitions. Validate guarded CREATE, PATCH/UPDATE, DELETE and subresource operations with real admission requests. RBAC authorization checks alone cannot demonstrate the guard. [Kubernetes authorization](https://kubernetes.io/docs/reference/access-authn-authz/rbac/), [validating admission policy](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/), [OKE controller support](https://docs.oracle.com/en-us/iaas/Content/ContEng/Reference/contengadmissioncontrollers.htm)

## Rehearsal, recovery and activation

1. Compare the recorded six Helm revisions to live release and retained manifests. At this checkpoint the revisions were 25, 14, 14, 14, 11 and 6 for OCI Jaeger, OTel Jaeger, OpenSearch, Dashboards, OTel application and monitoring. An upgrade plus rollback could require 26/27, 15/16, 15/16, 15/16, 12/13 and 7/8 respectively. Pruning may delete older retained records. Two Jaeger upgrades use `--atomic`. The other four releases need explicit failure inspection and targeted rollback. A successful OpenSearch engine upgrade followed by a failed Dashboards upgrade needs component-level recovery. Helm rollback does not downgrade migrated storage or restore custom-resource data.
2. Rehearse the proposed rights using isolated Kubernetes credentials and fixtures. Exercise the monitoring pre-upgrade and pre-rollback hook resources and chart-owned Secret handling, not only a Jaeger upgrade. Test a denied unrelated Secret mutation and unexpected privileged Job/RBAC/webhook spec. Verify the actual scheduled principal with nonpersistent server-side requests on OKE before activation. Keep recovery/operator access independent and remove broad RBAC before relaxing any admission guard.
3. The OpenSearch test requests **1.25 CPU and 6.5 GiB** on a node different from the live OpenSearch Pod and compatible with the restored block volume, plus any scheduler overhead. Check node allocation, topology and OCI attachment/storage limits. A local or kind run can exercise RBAC and admission, but OCI CSI backup, restore, scheduling and a real trace read require an OCI-backed rehearsal. The selected component creates a full retained backup and restore volume. These can incur charges and accumulate on successive OpenSearch updates. Keep deletion separate and review retained resources and costs after each run.
4. If capacity is insufficient, report the exact unschedulable reason. Prepare a separately costed, authorized temporary worker for the rehearsal, use existing suitable capacity when available, or explicitly revise the recovery policy through a separate reviewed change. A shell fix or successful mock does not establish restoration. Preserve existing routing, storage and synthetic-trace policy during routine updates.
5. Before the first scheduled write, capture all six releases and supplemental state, check that all five components can run or give a clear reason for each skip, and verify prior/candidate/rollback scope. After the first run inspect each release and component fingerprint plus fresh write/read traces, finite metrics under observed traffic, public UI, TLS, Grafana and Dashboards. On failure drain new writers, preserve successful siblings and restore only the affected release and its fingerprint after inspection.
